# Soperator 5.0 release notes

Soperator 5.0 moves clusters to Slurm 26.05 and CUDA 13.
It adds several network topologies per cluster, worker updates that wait for running jobs,
and per-job private temporary filesystems.
Login nodes gain per-user resource isolation, autoscaling and Docker.
GPU health checks now run as one job per node instead of many separate checks.
Much of the work in this release went into large clusters:
the operator and health checks put far less load on the Kubernetes API server and on slurmctld,
the exporter can read jobs from slurmdbd, and default Slurm settings are tuned for clusters with thousands of nodes.

5.0 is a major release with incompatible changes.
⚠️ marks a change that can affect an existing cluster or its configuration, followed by what to do.
🔧 marks how the [Nebius Terraform recipe](https://github.com/nebius/nebius-solutions-library/tree/soperator-release-5.0/soperator) for 5.0 sets up new clusters.

## Slurm

Slurm is upgraded from 25.11 to 26.05.6-nebius-1, a Nebius build of Slurm 26.05
([#2875](https://github.com/nebius/soperator/pull/2875), [#3297](https://github.com/nebius/soperator/pull/3297)).
The Nebius patches add a per-node `AutoResume` setting, node reboot through the REST API, and topology fixes.
⚠️ Check custom Slurm configuration and plugins against the Slurm 26.05 release notes.

Generated Slurm configuration has a new layout ([#2573](https://github.com/nebius/soperator/pull/2573)).
`/etc/slurm/slurm.conf` is now a stub that includes the generated `slurm_base.conf.noedit` and `slurm_k8s_extra.conf.noedit`.
The second file holds the custom overrides that 4.1 kept in `custom_slurm.conf`.
In the jail, `scontrol` now warns when a partition or node change will be lost at the next reconfigure
([#3090](https://github.com/nebius/soperator/pull/3090)).
See [Slurm configuration](../docs/slurm-configuration.md) for details.
⚠️ Tools that parse `slurm.conf` or `custom_slurm.conf` directly must read the new files or use `scontrol show config`.

Default Slurm settings are tuned for large, busy clusters
([#2763](https://github.com/nebius/soperator/pull/2763), [#3027](https://github.com/nebius/soperator/pull/3027)):

- slurmstepd manages job steps instead of slurmctld (`SlurmctldParameters=enable_stepmgr`).
  This requires `PrologFlags=contain`, so the prolog now runs on all nodes of a job when the job is allocated,
  and every job gets an `extern` step.
  ⚠️ Check custom prolog scripts that depend on the old timing.
- `MinJobAge` drops from 8 hours to 10 minutes.
  ⚠️ Finished jobs disappear from `squeue` and `scontrol show job` after 10 minutes.
  Use `sacct`, or set `slurmConfig.minJobAge` to keep the old value.
- `jobAcctGatherType` changes from `jobacct_gather/cgroup` to `jobacct_gather/none`, which makes job submission faster.
  4.1 already collected usage only when a job ended.
  ⚠️ `sstat` returns no data, and `sacct` no longer shows usage such as MaxRSS or AveCPU.
- Per-user RPC rate limiting is on, so one user cannot overload slurmctld.
- Other limits and scheduler parameters are tuned, and some, such as `MaxNodeCount` and `MaxArraySize`,
  scale with the number of workers
  ([#2503](https://github.com/nebius/soperator/pull/2503)).

A default task prolog writes each step's Slurm environment to the job logs and warns when a job is submitted from inside another job
([#2350](https://github.com/nebius/soperator/pull/2350)).
With the opt-in `slurmScripts.taskPrologEnv` setting,
the prolog also sources files and exports chosen environment variables into job tasks
([#3105](https://github.com/nebius/soperator/pull/3105)).
The task prolog also sets `DOCKER_HOST`, so `docker` in jobs uses the Docker proxy.
⚠️ If you use your own TaskProlog, export `DOCKER_HOST` the same way.

With `slurmdbdConfig.privateData` enabled, regular users can now see their own jobs in `sacct`
([#3298](https://github.com/nebius/soperator/pull/3298)).
Each user still needs a user record and association in the accounting database.

## Network topology

A SlurmCluster can now define several named topologies, and each partition uses one of them
([#2889](https://github.com/nebius/soperator/pull/2889)).
For example, InfiniBand GPU NodeSets can use a tree or block topology, and Ethernet CPU NodeSets a flat one.
NodeSets can also declare their InfiniBand fabric, so Slurm does not place a job across fabrics that are not connected
([#2585](https://github.com/nebius/soperator/pull/2585)).
See [Network topology](../docs/topology.md).
⚠️ `slurmConfig.topologyPlugin` and `topology.blockSize` are removed,
and Soperator no longer sets a topology by default (4.1 used `topology/tree`).
Declare your topologies in `topology.topologies` when you upgrade.
Tree and block topologies include GPU NodeSets only,
so a partition that mixes GPU and CPU-only NodeSets must use a flat topology and loses InfiniBand-aware placement;
put them in separate partitions to keep it.
🔧 The recipe generates `flat`,
`tree-ib` and `block-nvl72` topologies from the worker platforms and picks the cluster default;
partitions select a topology with the new `topology` field.

Topologies now follow the InfiniBand hierarchy more closely
([#3037](https://github.com/nebius/soperator/pull/3037), [#3164](https://github.com/nebius/soperator/pull/3164),
[#2987](https://github.com/nebius/soperator/pull/2987)).
Blocks and leaf switches are ordered by InfiniBand path, so on GB300 clusters Slurm's blocks match the physical layout.
The first node of a job holds rank 0, even when the partition does not use the cluster default topology.
The default `slurmConfig.topologyParam` changes from `SwitchAsNodeRank` to `BlockAsNodeRank,SwitchAsNodeRank`
([#3106](https://github.com/nebius/soperator/pull/3106)).

When the topology changes, the operator runs `scontrol reconfigure` only if Slurm needs it,
and groups changes that only reorder switches or blocks, so reconfigures stay rare
([#3164](https://github.com/nebius/soperator/pull/3164)).

## Jobs and containers

Jail and active check images are built for CUDA 13.0.3 only;
CUDA 12 is no longer supported
([#2989](https://github.com/nebius/soperator/pull/2989), [#2956](https://github.com/nebius/soperator/pull/2956)).
⚠️ Node GPU drivers must support CUDA 13 (driver 580 or later).

Each job now gets its own tmpfs at `/tmp`, `/dev/shm` and `/mnt/memory`
([#3083](https://github.com/nebius/soperator/pull/3083)).
They count toward the job's memory limit and are removed when the job ends,
so files that a job leaves behind no longer use node memory or disk.
Set `namespaceConfig.enabled: false` to turn this off.
⚠️ `/tmp` is now in memory, so jobs that write large temporary files there need enough memory for them.
The `/mnt/memory/job_<id>` directories that 4.1 created for each job are gone; use `/mnt/memory` directly.
Jail submounts at or below these paths are hidden from jobs.

This release also reworks how containers run on workers.

`docker run` inside a Slurm job now places the container in the job's cgroup,
so containers respect the job's CPU and memory limits
([#2344](https://github.com/nebius/soperator/pull/2344)).
The Docker daemon runs chrooted into the jail and sees the same filesystem as users,
which makes workflows such as `docker compose` work
([#2354](https://github.com/nebius/soperator/pull/2354)).
Login and worker nodes share a new Docker proxy that supports `attach` and `exec` streaming
([#2893](https://github.com/nebius/soperator/pull/2893)).
Docker can be disabled per NodeSet with `docker.enabled`, for nodes without image storage disks
([#2694](https://github.com/nebius/soperator/pull/2694)).
⚠️ Images now bundle their supervisord configuration,
and the soperator-custom-configmaps chart no longer creates `custom-supervisord-config`.
Remove `configMapRefSupervisord` from NodeSets that point to it, or they fail to reconcile.
🔧 The recipe no longer creates image storage disks, so workers have no Docker by default;
in 4.1 the example created a 930 GiB image disk on each worker.
Set `node_local_image_disk.enabled` on a worker NodeSet, or `slurm_login_image_disk.enabled` for login nodes,
to enable Docker there.

Enroot and Pyxis containers can now start directly from cached SquashFS images with squashfuse and an overlay,
instead of unpacking them
([#2562](https://github.com/nebius/soperator/pull/2562)).
Containers whose image is cached then start almost instantly,
and nodes no longer need a disk to hold unpacked Enroot images.
The feature is off by default in the slurm-cluster chart; enable it with `plugStackConfig.pyxis.useSquashfuse`.
Multi-node container jobs also start faster:
nodes that find the image cached no longer wait on an exclusive lock,
and concurrent jobs that need the same missing image import it once
([#2820](https://github.com/nebius/soperator/pull/2820)).
🔧 The recipe enables it by default (`enroot_direct_squashfs_enabled`).

The new `soperator-nccl-test` command in the jail runs a multi-node NCCL all-reduce test with settings for H100, H200,
B200, B300 and GB300
([#3121](https://github.com/nebius/soperator/pull/3121)).

NVIDIA libraries mounted into the jail are now protected with dpkg diversions and mock packages instead of AppArmor rules,
so `apt` can install GPU packages without overwriting them
([#3261](https://github.com/nebius/soperator/pull/3261), [#3254](https://github.com/nebius/soperator/pull/3254),
[#3273](https://github.com/nebius/soperator/pull/3273)).
CUDA forward-compatibility libraries are no longer mounted, so jobs use libraries that match the host driver
([#2636](https://github.com/nebius/soperator/pull/2636)).

The default resource limits on workers now apply to `root` too ([#3087](https://github.com/nebius/soperator/pull/3087)).
Pyxis containers no longer fail to start intermittently when concurrent jobs use NCCL debug logging
([#3290](https://github.com/nebius/soperator/pull/3290)).

## Login nodes and SSH access

Each regular SSH user (UID 1000 and above) on a login node now gets their own cgroup
([#2837](https://github.com/nebius/soperator/pull/2837), [#2938](https://github.com/nebius/soperator/pull/2938)).
Root and system users are not limited.
A user's memory is throttled above 40% of the sshd container memory,
and at 50% the OOM killer acts only inside that user's cgroup.
CPU is not limited, but under contention it is shared equally between users.
As a result, a runaway process affects only its owner, not every session on the login pod.
This needs cgroup v2.
The slurm-cluster chart enables it by default; the settings are in `slurmNodes.login.userIsolation`.

SSH sessions on login and worker nodes now enter the jail through a PAM module instead of the OpenSSH `ChrootDirectory` setting,
so Enroot works in them
([#2901](https://github.com/nebius/soperator/pull/2901)).
⚠️ `ChrootDirectory` is removed from custom sshd configs (`slurmNodes.login.sshdConfigMapRefName`,
NodeSet `configMapRefSshd`), and they must contain `UsePAM yes`;
otherwise sessions are not confined to the jail.

Login pods can scale out automatically under CPU load with `slurmNodes.login.autoscaling`
([#2917](https://github.com/nebius/soperator/pull/2917)).
They never scale down on their own, so active sessions are not cut.
See [Login autoscaling](../docs/login-autoscaling.md).

Docker can be enabled on login nodes with `slurmNodes.login.docker.enabled`
([#2893](https://github.com/nebius/soperator/pull/2893)).
Containers are placed in the cgroup of the user who started them.

Workers can optionally use `pam_slurm_adopt` ([#3013](https://github.com/nebius/soperator/pull/3013)).
Non-root users can then SSH to a worker only while they have a job there;
the session joins the job's cgroup and ends with the job.
It is disabled by default and is configured in `pamSlurmAdopt`, including exempt users and groups.

Fixes:

- The slurm-cluster chart passes `slurmNodes.login.sshdConfigMapRefName` to the cluster again;
  since 3.0 it was silently ignored ([#3260](https://github.com/nebius/soperator/pull/3260)).
- SSH from login nodes to workers of NodeSets not named `worker` no longer stops at an unknown host key prompt,
  which broke non-interactive SSH
  ([#3269](https://github.com/nebius/soperator/pull/3269)).

## Rolling updates

This release starts the work on worker updates that do not interrupt running jobs; later releases will extend it.
The new NodeSet update strategy `slurmAwareRollingUpdate` replaces a worker pod only after its jobs finish
([#2887](https://github.com/nebius/soperator/pull/2887)).
Drains set by administrators or health checks are kept.
NodeSets with this strategy also get a PodDisruptionBudget, so Kubernetes node drains,
for example during node group upgrades, wait for running Slurm jobs
([#2962](https://github.com/nebius/soperator/pull/2962)).
The new "Soperator / Rollouts" dashboard shows rollout progress and stuck workers
([#3021](https://github.com/nebius/soperator/pull/3021)).
The strategy applies to worker NodeSets only.
The nodesets chart keeps `rollingUpdate` as the default.
See [Slurm-aware worker rolling updates](../docs/worker-node-rollout.md).
🔧 The recipe uses `slurmAwareRollingUpdate` for worker NodeSets,
and Kubernetes node group upgrades also wait for running jobs, with no drain time limit (`drain_timeout = "0s"`).

## Workers, NodeSets and power management

When a worker pod restarts, Soperator no longer undrains the Slurm node or clears its reason and comment
([#2887](https://github.com/nebius/soperator/pull/2887)).
⚠️ Nodes drained by an administrator or a health check stay drained;
return them to service with `scontrol update nodename=<node> state=resume`.

Worker startup is gentler on slurmctld.
`maxUnavailable`, whose default changes from `20%` to `500`, now also limits how many workers start at the same time
([#2537](https://github.com/nebius/soperator/pull/2537), [#2887](https://github.com/nebius/soperator/pull/2887)).
The new NodeSet field `workerInitRandomDelaySeconds` makes each worker wait a random 0 to N seconds before starting,
which spreads slurmd registrations after cluster-wide restarts
([#2619](https://github.com/nebius/soperator/pull/2619), [#3363](https://github.com/nebius/soperator/pull/3363)).
The default is 30 seconds; set it to 0 to turn the delay off.

The nodesets chart can generate a series of NodeSets from one entry with `range`, for example one NodeSet per GB300 rack
([#3126](https://github.com/nebius/soperator/pull/3126)).
The new `aggregateSlurmNodeSets` setting lets partitions and topologies refer to one Slurm NodeSet that spans several NodeSets,
so adding racks needs no partition changes
([#3134](https://github.com/nebius/soperator/pull/3134)).

Power management of ephemeral nodes is more reliable ([#2949](https://github.com/nebius/soperator/pull/2949)).
The power manager now waits for a new NodeSet `PowerStateReady` condition,
which confirms that the worker pods are ready or deleted.
The wait uses `slurmConfig.resumeTimeout` and the new `slurmConfig.suspendTimeout`.
⚠️ NodeSets now render `AutoResume=Off` for their nodes
([#2880](https://github.com/nebius/soperator/pull/2880), [#2995](https://github.com/nebius/soperator/pull/2995)).
Slurm no longer powers up ephemeral nodes for queued jobs;
such jobs stay pending until the nodes are powered up with `scontrol power up`.
To keep automatic power-up, set `nodeConfig.autoResume: true` on the NodeSet.
🔧 The recipe now creates ephemeral worker NodeSets,
with one worker per NodeSet powered up when the cluster is created (`initial_number_ephemeral_nodes = 1`);
in 4.1 the example used static workers.
Except on GB300, worker node groups autoscale,
so powering a worker down deletes its VM and powering it up creates a new one.
Set `auto_resume = true` to keep automatic power-up.

Static workers that were powered down with `scontrol power down`, or failed to resume,
now return to service automatically
([#3262](https://github.com/nebius/soperator/pull/3262)).
Switching a static NodeSet to ephemeral mode now keeps its running workers,
and switching back to static mode is supported
([#2902](https://github.com/nebius/soperator/pull/2902)).
⚠️ Static workers, NodeSets with `ephemeralNodes: false`, are deprecated and will be removed in a future release.
Set `ephemeralNodes: true` to move a NodeSet to ephemeral mode.

Partitions that refer to NodeSets that do not exist yet, or have zero replicas, no longer produce an invalid slurm.conf
([#2861](https://github.com/nebius/soperator/pull/2861)).
Unresolved references are reported in the new `NodeSetRefsResolved` SlurmCluster condition.

## Health checks and node remediation

GPU active checks are consolidated into a single `gpu-checks` job that runs on every worker at 00:00 and 12:00,
occupying nodes far less often than the separate checks of 4.1
([#2720](https://github.com/nebius/soperator/pull/2720)).
The job also runs the InfiniBand GPU performance tests, so a failing node is drained instead of only getting a comment
([#2754](https://github.com/nebius/soperator/pull/2754)).
A `gpu_checks` Slurm license limits how many run at the same time:
slurm.conf gets `Licenses=gpu_checks:200` by default, and a `Licenses=` line in `customSlurmConfig` replaces it
([#3034](https://github.com/nebius/soperator/pull/3034)).
On CPU-only clusters, GPU checks are marked Skipped instead of failing and blocking installation,
and on mixed clusters they are submitted only to GPU nodes
([#2408](https://github.com/nebius/soperator/pull/2408), [#2683](https://github.com/nebius/soperator/pull/2683)).
⚠️ `gpu-checks` replaces `cuda-samples`, `all-reduce-perf-nccl-with-ib`, `all-reduce-perf-nccl-without-ib`,
`dcgmi-diag-r2`, `gpu-fryer`, `mem-perf` and `ib-gpu-perf`;
move overrides of these checks to `checks.gpu-checks`.
If `customSlurmConfig` sets `Licenses=`, add `gpu_checks:200` to that line,
otherwise gpu-checks jobs cannot be submitted.
`dcgmi-diag-r3`, which 4.1 ran only on demand, is no longer created;
set `checks.dcgmi-diag-r3.enabled: true` to keep it.
🔧 The recipe no longer runs GPU health checks at cluster creation (`active_checks_scope = "essential"`);
they still run on their schedule.
Use `prod_quick` or `prod_acceptance` to check GPUs before the cluster is handed over.
In 4.1 the default scope was `prod_quick`.

New passive checks:

- `idle_mem_used` drains an idle node whose available memory has dropped below its Slurm `RealMemory`,
  which catches memory held by leftover processes
  ([#2773](https://github.com/nebius/soperator/pull/2773)).
  It replaces `alloc_mem_used` and drains with the same reason, `[user_problem] alloc_mem_used`.
- `nvidia_libraries` drains GPU workers whose NVIDIA driver libraries in the jail are empty or missing,
  and undrains them once the libraries are restored
  ([#3078](https://github.com/nebius/soperator/pull/3078)).
- `drop_posix_shmem` now also runs in the prolog and for CPU jobs that take whole nodes,
  so leftover `/dev/shm` is cleaned before exclusive jobs start
  ([#2943](https://github.com/nebius/soperator/pull/2943)).
  Custom checks can use the new option `skip_for_partial_cpu_jobs`.

Removed checks:

- Active checks:
  the extensive-check pipeline and its `suspicious-node` reservation, `prepull-container-image`,
  `all-reduce-perf-nccl-in-docker`, `enroot-cleanup`, `ssh-check`, `ensure-dir-snccld-logs`, `upgrade-health-checker`,
  `wait-for-topology` and `soperator-outputs-logs-cleaner`
  ([#2671](https://github.com/nebius/soperator/pull/2671), [#2764](https://github.com/nebius/soperator/pull/2764),
  [#2782](https://github.com/nebius/soperator/pull/2782), [#2676](https://github.com/nebius/soperator/pull/2676),
  [#2720](https://github.com/nebius/soperator/pull/2720), [#2889](https://github.com/nebius/soperator/pull/2889)).
  Workload outputs are now cleaned on the worker boot disks;
  the new `nccl-profiles-cleaner` check only removes empty NCCL Inspector dump directories.
- Passive checks:
  `alloc_mem_used`, `cleanup_enroot` and `nvme_raid_health`
  ([#2778](https://github.com/nebius/soperator/pull/2778), [#2782](https://github.com/nebius/soperator/pull/2782),
  [#2905](https://github.com/nebius/soperator/pull/2905)).
  ⚠️ The slurm-cluster chart now fails to render if `slurmScripts.builtIn` enables a script that no longer exists,
  including `job_tmpfs_*`, `map_job_dcgm.sh` and `unmap_job_dcgm.sh`
  ([#2779](https://github.com/nebius/soperator/pull/2779));
  remove such entries.

Workers drained with a `[node_problem]` reason are no longer deleted from Kubernetes by Soperator
([#3192](https://github.com/nebius/soperator/pull/3192)).
They stay cordoned until the platform marks the host unhealthy and replaces it,
and the report to the platform carries the drain reason.
Reporting hosts as unhealthy is controlled by `checks.manager.enableNodeReplacement` in the soperatorchecks chart,
off by default.
⚠️ `checks.manager.enableExtensiveCheck` is removed:
a drained worker is now reported as soon as it has drained, without a confirming extensive check in a reservation.
🔧 As in 4.1, the recipe enables reporting unhealthy hosts except on clusters with GB300 workers,
where the platform cannot yet take reports of unhealthy hosts.
On those clusters, workers that fail health checks stay drained until an administrator handles them.

Checks with `on_ok: undrain` or `on_ok: uncomment` now clear the reason or comment they set
([#2955](https://github.com/nebius/soperator/pull/2955)).
GB300 workers now get the same active and passive checks as other platforms.

## Observability

Soperator now supports NCCL Inspector for per-job NCCL performance profiling
([#2553](https://github.com/nebius/soperator/pull/2553), [#2464](https://github.com/nebius/soperator/pull/2464),
[#2471](https://github.com/nebius/soperator/pull/2471), [#2612](https://github.com/nebius/soperator/pull/2612)).
It is enabled by default, but a job is profiled only when it sets `NCCL_INSPECTOR_ENABLE=1`
([#3337](https://github.com/nebius/soperator/pull/3337)).
A collector turns the profiles into metrics in the in-cluster VictoriaMetrics, and new Grafana dashboards show them.
The plugin is configured with `plugStackConfig.ncclInspectorPreConf`, the collector with `observability.ncclProfiles`.

Slurm workload outputs (prolog, epilog, HealthCheckProgram and active check job logs,
NCCL debug logs) are now written to the worker's boot disk, under `/opt/soperator-outputs/local` in the jail,
and collected by an agent on every worker, which offloads log traffic from the shared filesystem
([#2816](https://github.com/nebius/soperator/pull/2816)).
⚠️ Update tools that read these files from the shared filesystem.

The OpenTelemetry collectors keep exporter queues on disk, so telemetry survives collector restarts and backpressure
([#2641](https://github.com/nebius/soperator/pull/2641)).
Log collectors send larger batches, with a separate limit for the Nebius logging endpoint
([#2504](https://github.com/nebius/soperator/pull/2504)).
The token writer that 4.1 ran for metrics now also maintains the token for log and event collectors,
and reads it from instance metadata by default
([#2800](https://github.com/nebius/soperator/pull/2800)).
⚠️ In soperator-fluxcd, `observability.vmStack.tsaToken` is replaced by `observability.tsaToken`; move its settings.
The writer's default source changes from `file` to `imds`;
set `observability.tsaToken.writer.source: file` if your nodes provide the token as a host file.

Exporter improvements:

- The exporter can read jobs from slurmdbd instead of slurmctld,
  which reduces load on the controller in large clusters (`slurmNodes.exporter.jobSource: accounting`)
  ([#2502](https://github.com/nebius/soperator/pull/2502)).
  Some job labels are less detailed than with the default `controller` source,
  see the [exporter docs](../docs/slurm-exporter.md).
- Collectors run independently, so one failing or slow Slurm API call no longer drops or delays other metrics.
  The exporter reports errors and latency per collector
  ([#2630](https://github.com/nebius/soperator/pull/2630), [#2722](https://github.com/nebius/soperator/pull/2722)).
- The new `slurm_node_nvlink_instance_group` metric and an `nvlink_instance_group` label on `slurm_node_job` allow per-NVLink-domain views
  ([#2864](https://github.com/nebius/soperator/pull/2864)).
- `slurm_node_info` and `slurm_node_job` gain a `nodeset_name` label
  ([#2870](https://github.com/nebius/soperator/pull/2870)).

DCGM GPU metrics no longer carry the `hpc_job` label;
the bundled dashboards join them with the exporter's `slurm_node_job` metric instead
([#2923](https://github.com/nebius/soperator/pull/2923)).
⚠️ Update queries and alerts that use `hpc_job`.

ServiceMonitors now set a `component` label, and sconfigcontroller metrics are scraped again
([#3049](https://github.com/nebius/soperator/pull/3049)).
New metrics attribute Kubernetes API and slurmrestd requests to the controller that sent them
([#3053](https://github.com/nebius/soperator/pull/3053), [#3058](https://github.com/nebius/soperator/pull/3058)).
soperator and soperatorchecks now serve their metrics themselves on port 8443 with built-in authentication,
and the kube-rbac-proxy sidecar is removed;
scraping still requires RBAC access to `/metrics` ([#2624](https://github.com/nebius/soperator/pull/2624)).
⚠️ Three values of the `controller` label in metrics and logs are renamed; update alerts and dashboards that use them.

Dashboards:

- New "Soperator / Controllers" dashboard with reconciles,
  work queues and leader election for every Soperator controller
  ([#3049](https://github.com/nebius/soperator/pull/3049)).
- New NodeSets overview dashboard, and a NodeSet dimension in existing dashboards, for per-rack views on GB300
  ([#2870](https://github.com/nebius/soperator/pull/2870)).
- New dashboard for exporter health ([#3077](https://github.com/nebius/soperator/pull/3077)).
- Node counts by Slurm state, including power and CLOUD flags ([#2958](https://github.com/nebius/soperator/pull/2958)).
- A datasource selector on every dashboard ([#2864](https://github.com/nebius/soperator/pull/2864)).
- Grafana dashboards no longer lose their VictoriaMetrics datasource
  ([#3215](https://github.com/nebius/soperator/pull/3215)).

## Large clusters

Many changes in this release remove load that grew with cluster size.

On the Kubernetes API server:

- The operator and soperatorchecks read Nodes from their informer cache instead of paging through LIST calls
  ([#2919](https://github.com/nebius/soperator/pull/2919)).
- They no longer watch Helm release Secrets ([#3094](https://github.com/nebius/soperator/pull/3094)).
- The topology controller reconciles only when a node's topology labels change, not on every Node update
  ([#2631](https://github.com/nebius/soperator/pull/2631)).
- The pod ephemeral storage check reads disk usage from each node's kubelet directly instead of through the API server
  ([#2888](https://github.com/nebius/soperator/pull/2888)).
- Each rebooter caches only its own Node instead of every Node and Pod in the cluster,
  and lists the node's pods from the local kubelet
  ([#2497](https://github.com/nebius/soperator/pull/2497), [#2796](https://github.com/nebius/soperator/pull/2796),
  [#2910](https://github.com/nebius/soperator/pull/2910)).
- The operator now limits its Kubernetes API client to 30 requests per second with a burst of 50;
  4.1 had no client-side limit.
  Change it with `--rest-config-qps` and `--rest-config-burst` in `controllerManager.manager.args`
  ([#2949](https://github.com/nebius/soperator/pull/2949)).
- OpenKruise is installed from a Soperator-maintained chart that runs its manager with `--rest-config-qps=100` and `--rest-config-burst=200`,
  so worker pods keep getting scheduled on clusters with thousands of nodes
  ([#2494](https://github.com/nebius/soperator/pull/2494)).

On slurmctld:

- Active checks poll job status through slurmdbd and no longer re-list processed jobs
  ([#2508](https://github.com/nebius/soperator/pull/2508), [#2527](https://github.com/nebius/soperator/pull/2527)).
- Passive checks in prolog and epilog no longer query the node for undrain actions
  ([#2719](https://github.com/nebius/soperator/pull/2719)).
- The pod ephemeral storage check reads Slurm node states from one shared node list per cluster instead of sending one request per worker pod
  ([#2500](https://github.com/nebius/soperator/pull/2500)).
- The slurmctld liveness probe uses the native `/livez` endpoint instead of `scontrol ping`
  ([#2501](https://github.com/nebius/soperator/pull/2501)).

slurm.conf uses one `NodeName` line per NodeSet, which keeps it under the ConfigMap size limit
([#2540](https://github.com/nebius/soperator/pull/2540)).
Node-exporter is scraped through EndpointSlices, so host metrics work on clusters with more than 1,000 nodes
([#2939](https://github.com/nebius/soperator/pull/2939)).

The NFS server raises its connection limit to 8192 by default,
configurable through `nfs.maxConnections` in the nfs-server chart,
and its StorageClass mounts with `nconnect=8` instead of 16
([#3063](https://github.com/nebius/soperator/pull/3063)).

🔧 In the recipe, resources of system components and the presets of system, controller,
accounting and NFS nodes scale with the number of workers,
in sizing tiers from XS (fewer than 10 workers) to XL (2,000 or more).
Set `sizing_tier_override` to force a tier, or `component_overrides` to change individual components.
NFS is rejected on clusters with 500 or more workers.

## Installation and Helm

Soperator is built with Kubernetes 1.36 libraries and requires Kubernetes 1.35 or later
([#2784](https://github.com/nebius/soperator/pull/2784), [#3005](https://github.com/nebius/soperator/pull/3005)).
The bundled cert-manager moves to 1.21, and check jobs ship kubectl 1.36.
⚠️ Upgrade Kubernetes to 1.35 or later before upgrading Soperator.

Several SlurmClusters can run in one namespace
([#2182](https://github.com/nebius/soperator/pull/2182), [#3000](https://github.com/nebius/soperator/pull/3000)).
NodeSets refer to their cluster through `spec.clusterName`.
To avoid name collisions,
set `podNamePrefix: enabled` (`spec.podNamePrefix` on the SlurmCluster) so cluster workloads are prefixed with the cluster name.
NodeSet names must still be unique within the namespace.
The default is `disabled`, which keeps the names of 4.1.
Choose the mode when creating the cluster.
⚠️ New NodeSets must set `spec.clusterName` (`clusterName` in the nodesets chart,
`nodesets.clusterName` in soperator-fluxcd), because the mutating webhook that filled it in is removed.

The Security Profiles Operator is no longer installed or used ([#2983](https://github.com/nebius/soperator/pull/2983)).
The login sshd and worker slurmd containers use the AppArmor profile named in `slurmNodes.login.sshd.appArmorProfile` and in the NodeSet `slurmd.security.appArmorProfile`,
and the profile must be loaded on every node.
See [AppArmor](../docs/apparmor.md) for how to set it up.
⚠️ `useDefaultAppArmorProfile` is removed and both fields default to `unconfined`;
set them to keep these containers confined.
After an in-place upgrade, clean up the leftover SPO CRDs and `AppArmorProfile` resources.
🔧 The recipe loads a profile named `soperator-default` through cloud-init and sets both fields.

Control-plane components installed by soperator-fluxcd are pinned to system nodes and have CPU request floors,
so they no longer take capacity from workers
([#2865](https://github.com/nebius/soperator/pull/2865), [#2772](https://github.com/nebius/soperator/pull/2772)).
The node-configurator rebooter gets its own PriorityClass, so it can always be scheduled on a packed node.
⚠️ These pods now run only on nodes with matching `slurm.nebius.ai/nodeset` labels.
Label the nodes the way the recipe does.
🔧 The recipe sets these labels.

OpenKruise is upgraded to 1.9 and installed from a Soperator-maintained chart in `oci://cr.nebius.cloud/soperator` instead of the upstream repository
([#3062](https://github.com/nebius/soperator/pull/3062), [#2494](https://github.com/nebius/soperator/pull/2494)).
Its webhooks now apply only to the Slurm cluster namespace,
and Flux no longer reports drift for fields that OpenKruise changes at runtime
([#3271](https://github.com/nebius/soperator/pull/3271)).
Every HelmRelease in soperator-fluxcd accepts a `postRenderers` value for Kustomize patches.
⚠️ If you mirror Helm repositories, mirror the new OpenKruise chart and update `helmRepository.kruise.url` overrides.
If you mirror images, add `cr.nebius.cloud/soperator-proxy-docker-io/prom/node-exporter`;
the kube-rbac-proxy image is no longer used.

Webhooks are controlled by `controllerManager.manager.env.enableWebhooks` (default `"true"`) instead of `certManager.enabled`
([#2827](https://github.com/nebius/soperator/pull/2827)),
so they can run with a serving certificate from another source.
⚠️ If you install the soperator chart with `certManager.enabled: false`,
provide a certificate or set `enableWebhooks: "false"`.

Worker pods run under a per-NodeSet service account, `<cluster>-<nodeset>-nodeset-sa`,
which can read and patch only that NodeSet's pods
([#2885](https://github.com/nebius/soperator/pull/2885)).
⚠️ Bindings that target the former `<cluster>-worker-sa` no longer apply.

`imagePullSecrets` and `imagePullPolicy` can be set for Soperator workloads, for example to use a private registry
([#2718](https://github.com/nebius/soperator/pull/2718)).
FluxCD timeouts and retries are raised, so installs and upgrades on large clusters fail less often
([#2642](https://github.com/nebius/soperator/pull/2642)).

🔧 The recipe no longer enables jail backups (`backups_enabled = "force_disable"`);
in 4.1 the example enabled them automatically.
